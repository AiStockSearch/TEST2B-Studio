# Решения и допущения

Итоговый список для сдачи. Подробности по базе и фронту — в `docs/ASSUMPTIONS.md`.

## Стек (где ТЗ оставляло выбор)

- **Next.js 15** (App Router, Server Actions, TypeScript) — вместо Vite: серверные действия, middleware сессии, один деплой на Vercel.
- **shadcn/ui** + Tailwind CSS 4 — аккуратный UI без оценки дизайна по ТЗ.
- **Zustand** — только клиентское UI-состояние (вид списка объектов); фильтры живут в URL query; права в нём не проверяются.
- **Prisma 7** (`@prisma/adapter-pg`) — серверный доступ к Postgres. Схема ведётся **только** SQL-миграциями `supabase/migrations`; `prisma migrate` не используется. Каждый запрос в транзакции: `SET LOCAL ROLE authenticated` + `set_config('request.jwt.claims', …)` (`withRls`), иначе RLS обошёлся бы.
- **Два драйвера** за интерфейсом `Repo`: `prisma` (прод, Session pooler) и `supabase` (PostgREST + JWT). Причина: в среде разработки исходящий Postgres был закрыт; оба пути опираются на одни RLS и триггеры.
- **Google Stitch** для макетов экранов — не сработал (таймаут генерации). Интерфейс собран на стандартном shadcn без отдельного дизайн-прохода.

## База и безопасность

- Смена статуса только через RPC `change_task_status`; колонка `status` не в `GRANT UPDATE`.
- Комментарий к переходу — через транзакционный `set_config('app.status_comment')`; BEFORE-триггер `tasks_guard` проверяет таблицу переходов и для rework требует комментарий; AFTER пишет историю.
- Хелперы RLS перенесены в схему `private` (Advisor 0029); из API вызывается только `change_task_status`.
- `FORCE ROW LEVEL SECURITY` на всех пяти таблицах; `anon` без прав.
- Открытая регистрация выключена в Dashboard; UI signup нет. `service_role` в приложении и репозитории не используется.
- Пользователей создаёт администратор в Supabase Auth; профили — seed / вручную (авто-триггера профиля нет).

- **Фото к задачам** — Supabase Storage, приватный bucket `task-photos` + таблица `task_attachments` (brief/result). RLS и политики storage: исполнитель видит фото только своих задач, добавляет фото результата только к своей задаче «В работе»/«На доработке», не удаляет. JPG/PNG/WebP, до 5 МБ, до 5 фото на задачу и тип. Показ через signed URLs.

## Допущения, которых нет в ТЗ

- При «Отправить на проверку» фото и комментарий необязательны.

- Исполнитель задачи — только роль `worker`.
- Любой постановщик видит и обрабатывает все объекты/задачи (в т.ч. чужие).
- Правка полей задачи запрещена в `accepted`; переназначение запрещено в `review`.
- Статус и другие поля одним UPDATE менять нельзя.
- `author_id` / `created_by` / `created_at` / `id` неизменяемы; при INSERT автор = `auth.uid()`.
- Удаление объекта с задачами — `ON DELETE RESTRICT`; удаление задачи каскадно чистит историю.
- Профили видны всем вошедшим (имена в карточках), менять профиль клиент не может.
- Ограничения длины полей и необязательный комментарий на переходах кроме rework — см. ASSUMPTIONS.
- «Мои задачи» у постановщика показывают все задачи (пункт меню «Все задачи»); у исполнителя после входа открываются «Мои задачи», у постановщика — «Объекты».
- Даты в UI — часовой пояс Asia/Yekaterinburg.

## Что не сделано / что улучшил бы

- Пагинация списков, realtime-обновления статусов, UI управления пользователями.
- Строгая проверка CA при TLS к pooler (сейчас `rejectUnauthorized: false`).
- Отдельный дизайн-проход (Stitch не отдал макеты).
- Leaked password protection в Supabase Auth — имеет смысл включить по Advisor (на логику CRM не влияет).
- При росте нагрузки — вынести пул соединений / уменьшить cold start serverless; сейчас `max: 3` на инстанс.
