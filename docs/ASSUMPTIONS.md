# Решения и допущения по базе данных

## Стек и доступ к БД
- Фронт/сервер: Next.js + Prisma + Zustand. Схема БД живёт **только** в чистых SQL-миграциях `supabase/migrations` (RLS, триггеры, RPC). Prisma используется только для `prisma db pull` и типов; `prisma migrate` для схемы не применяется.
- **Каждый серверный запрос Prisma выполняется в транзакции** с `SET LOCAL ROLE authenticated` и `select set_config('request.jwt.claims', <claims из проверенного JWT пользователя>, true)`. Тогда RLS и триггеры работают так же, как при запросе через Supabase API. Если подключиться напрямую под `postgres`, RLS обходится, поэтому так делать нельзя. Это закрыто тестом в `supabase/tests` («Prisma-like query»).
- Zustand хранит только клиентское состояние: сессию и фильтры. Права в нём не проверяются.
- Строка подключения и ключи в репозиторий не попадают: в `.env.example` только имена переменных. `service_role` не используется ни во фронте, ни в серверном коде приложения.

## Смена статуса и комментарий
- Выбран вариант **RPC `change_task_status(task_id, new_status, comment)`** (SECURITY DEFINER, `search_path` зафиксирован). Прямой `UPDATE status` клиент сделать не может: колонка `status` не выдана в `GRANT UPDATE`, а это запрет на уровне привилегий, а не только политики.
- RPC кладёт комментарий в транзакционную настройку (`set_config('app.status_comment', …, true)`). Триггер на `tasks` читает её, проверяет переход и автора, а для rework требует непустой комментарий. AFTER-триггер пишет историю.
- Почему так: правила переходов проверяются в одном месте, в BEFORE-триггере, и действуют при любом пути записи. RPC остаётся единственным клиентским путём к статусу, и комментарий атомарно попадает в историю. Подделать настройку извне нельзя: PostgREST не даёт вызвать `set_config`. Даже если подделать, переход всё равно проверит триггер.
- Чужая задача для исполнителя в RPC выглядит как несуществующая («task not found»), поэтому существование задач не раскрывается.

## Правила, которых нет в ТЗ
- Исполнителем может быть только пользователь с ролью worker.
- Постановщик меняет поля задачи (название, описание, объект, исполнитель) в любом статусе, кроме двух случаев: **`review`**, где задача на проверке и переназначать нельзя, и **`accepted`**, где задача закрыта и доступна только для чтения. Переназначение в `in_progress`/`rework` разрешено, статус при этом не сбрасывается, а новый исполнитель продолжает работу.
- Изменение статуса и других полей одним запросом запрещено.
- `author_id`, `created_at`, `id` неизменяемы. Автор задачи и объекта всегда равен `auth.uid()`, переданное клиентом значение игнорируется.
- Любой постановщик может работать с любыми объектами и задачами, в том числе созданными другим постановщиком («видит всё»). Принимать или возвращать задачу может любой постановщик, не только автор.
- Удаление объекта, в котором есть задачи, запрещено (`ON DELETE RESTRICT`): сначала нужно удалить или перенести задачи. Удаление задачи каскадно удаляет её историю (FK `ON DELETE CASCADE`). Удалить историю напрямую через API нельзя.
- Профили видны всем вошедшим, потому что имена исполнителей и авторов нужны в карточках. Изменить профиль клиент не может, поэтому роль сам себе не поменять. Профили создаёт seed или администратор. Триггера автосоздания профиля нет.
- Ограничения длины: название до 200 символов, адрес до 500, описание до 5000, комментарий до 2000. Пустые названия запрещены.
- Комментарий при других переходах необязателен, но сохраняется, если передан.
- `anon` не имеет доступа ни к чему.

## RLS
- RLS включён на всех 4 таблицах, `FORCE ROW LEVEL SECURITY` тоже. Хелперы `is_manager()` и `has_task_in_object()` объявлены как SECURITY DEFINER, STABLE, `search_path = public`. Они читают `profiles`/`tasks` в обход RLS, поэтому рекурсии политик objects↔tasks нет.
- Риск: при FORCE RLS definer-функции работают только потому, что владелец (`postgres` в Supabase) имеет BYPASSRLS. Локально `postgres` является суперпользователем. При выкладке нужно проверить в облаке тем же тест-скриптом.
- Исполнитель вообще не имеет политики UPDATE на `tasks`: свои статусы он меняет только через RPC.

## Регистрация
- Локально: `supabase/config.toml` → `[auth] enable_signup = false`.
- Облако: Dashboard → Authentication → Sign In / Providers → выключить **Allow new users to sign up**. Пользователей создаёт администратор через Authentication → Users → Add user.

## Seed
- `supabase/seed.sql` берёт пользователей, созданных в Dashboard, по email (`manager@`, `worker1@`, `worker2@demo.local`), создаёт 3 объекта и 8 задач. Статусы задаются через `change_task_status` от имени нужного пользователя, поэтому история реалистичная. Пароли в репозитории не хранятся.

## Тесты
- `supabase/tests/rls_and_workflow.test.sql` проверяет 40 сценариев в одной транзакции с `rollback`. Скрипт рассчитан на пустую базу без seed. Для прогона на голом Postgres есть заглушки `supabase/local-stubs/` (роли anon/authenticated, `auth.users`, `auth.uid()`, дефолтные гранты как в Supabase) и `tests/run-local.sh`.
