# Решения и допущения по базе данных

## Стек и доступ к БД
- Фронт/сервер: Next.js + Prisma + Zustand. Схема БД живёт **только** в чистых SQL-миграциях `supabase/migrations` (RLS, триггеры, RPC). Prisma используется только для `prisma db pull` и типов; `prisma migrate` для схемы не применяется.
- **Каждый серверный запрос Prisma выполняется в транзакции** с `SET LOCAL ROLE authenticated` и `select set_config('request.jwt.claims', <claims из проверенного JWT пользователя>, true)`. Тогда RLS и триггеры работают так же, как при запросе через Supabase API. Если подключиться напрямую под `postgres`, RLS обходится, поэтому так делать нельзя. Это закрыто тестом в `supabase/tests` («Prisma-like query»).
- Zustand хранит только клиентское состояние: сессию и фильтры. Права в нём не проверяются.
- Строка подключения и ключи в репозиторий не попадают: в `.env.example` только имена переменных. `service_role` не используется ни во фронте, ни в серверном коде приложения.

## Смена статуса и комментарий
- Выбран вариант **RPC `change_task_status(task_id, new_status, comment)`** (SECURITY DEFINER, `search_path` зафиксирован). Прямой `UPDATE status` клиент сделать не может: колонка `status` не выдана в `GRANT UPDATE`, а это запрет на уровне привилегий, а не только политики.
- RPC кладёт комментарий в транзакционную настройку (`set_config('app.status_comment', …, true)`). Триггер на `tasks` читает её, проверяет переход и автора, а для rework требует непустой комментарий. AFTER-триггер пишет историю.
- Почему так: правила переходов проверяются в одном месте, в BEFORE-триггере, и действуют при любом пути записи. RPC остаётся единственным клиентским путём к статусу, и комментарий атомарно попадает в историю. Подделать настройку извне нельзя: PostgREST не даёт вызвать `set_config`. Даже если подделать, переход всё равно проверит триггер.
- Чужая задача для исполнителя в RPC выглядит как несуществующая («task not found»), поэтому существование задач не раскрывается.

## Правила, которых нет в ТЗ
- Исполнителем может быть только пользователь с ролью worker.
- Постановщик меняет поля задачи (название, описание, объект, исполнитель) в любом статусе, кроме двух случаев: **`review`**, где задача на проверке и переназначать нельзя, и **`accepted`**, где задача закрыта и доступна только для чтения. Переназначение в `in_progress`/`rework` разрешено, статус при этом не сбрасывается, а новый исполнитель продолжает работу.
- Изменение статуса и других полей одним запросом запрещено.
- `author_id`, `created_at`, `id` неизменяемы. Автор задачи и объекта всегда равен `auth.uid()`, переданное клиентом значение игнорируется.
- Любой постановщик может работать с любыми объектами и задачами, в том числе созданными другим постановщиком («видит всё»). Принимать или возвращать задачу может любой постановщик, не только автор.
- Удаление объекта, в котором есть задачи, запрещено (`ON DELETE RESTRICT`): сначала нужно удалить или перенести задачи. Удаление задачи каскадно удаляет её историю (FK `ON DELETE CASCADE`). Удалить историю напрямую через API нельзя.
- Профили видны всем вошедшим, потому что имена исполнителей и авторов нужны в карточках. Изменить профиль клиент не может, поэтому роль сам себе не поменять. Профили создаёт seed или администратор. Триггера автосоздания профиля нет.
- Ограничения длины: название до 200 символов, адрес до 500, описание до 5000, комментарий до 2000. Пустые названия запрещены.
- Комментарий при других переходах необязателен, но сохраняется, если передан.
- `anon` не имеет доступа ни к чему.

## RLS
- RLS включён на всех 4 таблицах, `FORCE ROW LEVEL SECURITY` тоже. Хелперы `is_manager()` и `has_task_in_object()` объявлены как SECURITY DEFINER, STABLE, `search_path = public` и лежат в схеме `private`, которая не опубликована в API. Так их нельзя вызвать через `/rest/v1/rpc` (замечание Supabase Advisor 0029, исправлено миграцией 0004). Из API вызывается только `change_task_status`, это сделано намеренно. Они читают `profiles`/`tasks` в обход RLS, поэтому рекурсии политик objects↔tasks нет.
- Риск: при FORCE RLS definer-функции работают только потому, что владелец (`postgres` в Supabase) имеет BYPASSRLS. Локально `postgres` является суперпользователем. В облаке это проверено: `postgres` там имеет `rolbypassrls = true`, и тест-скрипт `tests/rls_and_workflow.cloud.test.sql` проходит полностью.
- Исполнитель вообще не имеет политики UPDATE на `tasks`: свои статусы он меняет только через RPC.

## Регистрация
- Локально: `supabase/config.toml` → `[auth] enable_signup = false`.
- Облако: Dashboard → Authentication → Sign In / Providers → выключить **Allow new users to sign up**. Пользователей создаёт администратор через Authentication → Users → Add user.

## Seed
- `supabase/seed.sql` берёт пользователей, созданных в Dashboard, по email (`manager@`, `worker1@`, `worker2@demo.local`), создаёт 3 объекта и 8 задач. Статусы задаются через `change_task_status` от имени нужного пользователя, поэтому история реалистичная. Пароли в репозитории не хранятся.

## Тесты
- `supabase/tests/rls_and_workflow.test.sql` проверяет 40 сценариев в одной транзакции с `rollback`. Скрипт рассчитан на пустую базу без seed. Для прогона на голом Postgres есть заглушки `supabase/local-stubs/` (роли anon/authenticated, `auth.users`, `auth.uid()`, дефолтные гранты как в Supabase) и `tests/run-local.sh`.

## Облако (05.11)
- В проекте применены миграции 0001–0004. Заглушки из `local-stubs` в облако не применялись.
- Пользователей создают в Dashboard или SQL-скриптом вне репозитория. Пароли в репозитории не хранятся.
- Через REST от имени worker1 проверено:
  - вход проходит, worker1 видит только свои 4 задачи;
  - чужие задачи и их история возвращают пустой ответ;
  - PATCH title и DELETE возвращают 0 строк;
  - PATCH status, POST в tasks и history, DELETE history и PATCH своей роли получают 403;
  - запрещённый переход через RPC получает 403, вызов на чужую задачу возвращает ошибку `task not found`;
  - `rpc/is_manager` отвечает 404, а anon получает 401.
- Включить в Dashboard: Authentication → Sign In / Providers → выключить «Allow new users to sign up»; Auth → Password security → «Leaked password protection» (замечание Advisor).

## Фронтенд (Next.js)
- **Next.js App Router + Server Actions.** Все данные читаются и пишутся на сервере. В браузер попадают только `NEXT_PUBLIC_SUPABASE_URL` и publishable-ключ, нужные для входа.
- **Пользователь** определяется на сервере через `supabase.auth.getUser()`: токен проверяет сервер Auth, а не просто чтение cookie. Роль берётся из `profiles`. Middleware не пускает без сессии никуда, кроме `/login`.
- **Prisma 7 + `@prisma/adapter-pg`**, клиент генерируется в `src/generated/prisma` (в git не попадает, `postinstall` и `build` запускают `prisma generate`). Схема `prisma/schema.prisma` написана по миграциям вручную, потому что `db pull` из моей среды недоступен (см. ниже). При доступе к БД её можно сверить командой `npx prisma db pull`. `prisma migrate` не используется, схему ведут SQL-миграции.
- **Pooler.** Рекомендуется Session pooler (порт 5432): `SET LOCAL` и транзакции работают как обычно. С Transaction pooler (6543) обёртка тоже корректна, потому что всё делается внутри одной транзакции, а адаптер `pg` использует безымянные prepared statements. `?pgbouncer=true` для драйверного адаптера не нужен. Пул небольшой (`max: 3`) из-за serverless.
- **Два драйвера данных за одним интерфейсом `Repo`:** `prisma` (основной, при заданном `DATABASE_URL`) и `supabase` (PostgREST с JWT пользователя). Причина: в моей среде разработки исходящий протокол Postgres закрыт, работает только HTTPS. Поэтому локальный прогон приложения и e2e шли через драйвер `supabase`. Путь Prisma проверен так: `tsc` и `build`, плюс в облачной БД выполнены те же SQL-операторы, что выполняет `withRls` (`set local role authenticated` + claims от worker1): видно 4 своих задачи, 0 чужих, обновление чужих затронуло 0 строк. Оба драйвера опираются на одни и те же RLS и триггеры.
- **«Мои задачи» для постановщика**: страница показывает все задачи (в меню «Все задачи»), потому что по ТЗ постановщик видит всё. Исполнителю после входа открываются «Мои задачи», постановщику открываются «Объекты».
- **Фильтр** по статусу на «Моих задачах» по умолчанию «Все, кроме принятых» и запоминается в localStorage (Zustand persist). Поиск по объектам работает на клиенте.
- **Кнопки действий** строятся из `src/lib/workflow.ts`. Это зеркало `task_transition_actor()`, совпадение проверяет unit-тест. Комментарий для «Вернуть на доработку» обязателен и в форме, и в Server Action, и в триггере.
- **Редактирование задачи:** когда задача на проверке, исполнителя поменять нельзя (поле заблокировано, то же правило в БД). Принятую задачу постановщик не редактирует и не удаляет из UI. Удалить объект с задачами нельзя, пользователь получает понятное сообщение.
- **Чужая задача или объект** для исполнителя открывается как «Не найдено», без различия между «нет такой» и «нет доступа».
- **Шрифт:** Inter с кириллицей. Даты показываются в часовом поясе Asia/Yekaterinburg.

## Чего не сделано / ограничения
- Пагинации нет: для демо-объёма она не нужна.
- Нет управления пользователями из UI: пользователей создаёт администратор в Supabase.
- Нет realtime-обновлений: статус обновляется после действия или перезагрузки страницы.
- Путь Prisma не прогнан end-to-end из среды разработки из-за закрытого порта Postgres. Его нужно проверить после деплоя на Vercel (вход тремя ролями).
