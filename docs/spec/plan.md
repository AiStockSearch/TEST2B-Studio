# Plan
1. Стек: Vite + React + TypeScript, @supabase/supabase-js, react-query, react-router, лёгкий UI (без тяжёлой библиотеки). Деплой Vercel.
2. БД (supabase/migrations): enum ролей и статусов; таблицы; функция is_manager(); RLS-политики; триггер tasks_guard (проверка переходов, прав, запрет менять не-статусные поля исполнителем, комментарий при rework); триггер записи истории; RLS на history только SELECT.
3. Тесты политик: SQL (pgTAP-стиль или скрипт с SET ROLE/request.jwt.claims) + Node-скрипт, ходящий в REST API от имени исполнителя (чужие задачи, запрещённые переходы, правка/удаление истории, signup).
4. Фронт по экранам; кнопки действий считаются из той же таблицы переходов, что и в БД.
5. Seed: 1 постановщик, 2 исполнителя, 3 объекта, ~8 задач во всех статусах (пользователей создаёт администратор в Dashboard, пароли не в репо).
6. README, ASSUMPTIONS.md, объяснение для руководителя (полстраницы), шпаргалка для Славы.

## Уточнение стека (05.11)
- Next.js + Prisma ORM + Zustand. Схема и безопасность задаются только чистыми SQL-миграциями в `supabase/migrations` (RLS, триггеры, RPC). Prisma нужна для `db pull` и типов, `prisma migrate` не используется.
- Серверные запросы Prisma выполняются в `$transaction` с `SET LOCAL ROLE authenticated` и `set_config('request.jwt.claims', <claims из JWT пользователя>, true)`, чтобы действовали RLS и триггеры. Прямой коннект под postgres обходит RLS, поэтому так нельзя.
- Смена статуса идёт только через RPC `change_task_status`.
- Zustand хранит только клиентское состояние: сессию и фильтры. Строки подключения лежат только в env, в репозитории есть `.env.example` без значений.
